Manual Model Benchmark

A simple, self-contained prompt suite for testing a model or agent with realistic work. These prompts are intentionally longer than the first version: key facts appear early, requirements change later, suggestions get rejected, and the model must carry the final state through to its answer.

Use it: Copy one prompt → paste it into a fresh agent/model session → run it once → reveal Expected Result and compare. No preprocessing, files, scoreboard, metadata form, or backend. The Copy button now includes a fallback for local file:// pages.
Tip: the continuity tests are especially useful for spotting models that solve the immediate subproblem but forget a late correction or revive an earlier rejected requirement.

CODING 01

Repair an Order-Preserving Function

Code + exact output
Prompt
You are reviewing a Python helper in a production utility library.

Current implementation:
```python
def unique_preserve(items):
    return list(set(items))
```

Required behavior:
- Return each distinct item exactly once.
- Preserve the order of the FIRST appearance of each item.
- Do not sort the input or output.
- Inputs for this task are limited to hashable Python values such as strings and integers; you do not need to support lists or dictionaries as elements.
- Keep the implementation simple and readable.

It must pass:
```python
assert unique_preserve([3, 1, 3, 2, 1]) == [3, 1, 2]
assert unique_preserve(["b", "a", "b", "c"]) == ["b", "a", "c"]
assert unique_preserve([]) == []
```

A reviewer initially suggested `sorted(set(items))`, but that suggestion is explicitly rejected because it destroys first-seen order.

Do all of the following:
1. Explain the bug in the original implementation in one concise paragraph.
2. Provide a corrected implementation.
3. Explain the time-complexity expectation for normal hashable inputs.
4. Give the exact returned value for:
```python
unique_preserve([5, 5, 2, 9, 2, 5, 1])
```
5. Do not broaden the scope to unhashable elements.
Expected Result
The answer should preserve first-seen order and not sort. A typical solution is:
def unique_preserve(items):
    seen = set()
    out = []
    for item in items:
        if item not in seen:
            seen.add(item)
            out.append(item)
    return out
  • list(dict.fromkeys(items)) is also valid for the stated scope.
  • Expected average time is O(n) with hash-based membership.
  • Exact final value: [5, 2, 9, 1].
  • Using sorted(...) fails the requirement.

CODING 03

Security Review Without Losing the Fix

Diagnosis + safe code
Prompt
Review this Python endpoint helper. The value of `host` comes directly from an HTTP request parameter.

```python
import subprocess

def ping_host(host):
    cmd = f"ping -c 1 {host}"
    return subprocess.check_output(cmd, shell=True, text=True)
```

Requirements from the security review:
1. Identify the primary vulnerability and explain why it exists.
2. Rewrite the function so it does not invoke a shell and passes arguments as a list.
3. Validate that `host` is either a syntactically valid IPv4/IPv6 address or an allowed hostname before invoking ping.
4. Keep the function focused; do not redesign the whole service.

LATE SECURITY NOTE:
For this benchmark, do NOT provide an executable command-injection payload. You may describe the attack class conceptually, but the final answer should stay defensive.

Return:
- Vulnerability
- Why it happens
- Corrected function
- One paragraph on validation
- One sentence on why `shell=False` plus argument separation changes the risk
Expected Result
  • Primary issue: OS command injection from untrusted input interpolated into a shell command with shell=True.
  • Corrected code should call something like subprocess.check_output(["ping", "-c", "1", host], text=True) without a shell.
  • Strong validation uses ipaddress.ip_address() for IPs and an allow-list or strict hostname validation for names.
  • The answer should honor the late note and not provide an executable injection payload.

SYSADMIN 01

Disk Full but du Does Not Agree

Diagnosis + safe remediation
Prompt
A Linux application server reports a nearly full `/var` filesystem after a log rotation event.

Evidence:
```text
$ df -h /var
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdb1        80G   78G  2.0G  98% /var

$ sudo du -xsh /var
12G     /var

$ sudo lsof +L1 | head
COMMAND PID  USER  FD  TYPE DEVICE   SIZE/OFF NLINK NAME
java    813  app   11w REG  8,17 64424509440     0 /var/log/app.log (deleted)

$ systemctl status app.service --no-pager
Active: active (running)
Main PID: 813 (java)
```

Operational constraints:
- The application can tolerate a graceful service restart during this maintenance window.
- Do not delete random files merely because `df` is high.
- Do not reboot the server unless a much safer targeted action fails.

Explain:
1. Why `df` and `du` disagree.
2. What the `(deleted)` row with `NLINK 0` means.
3. The safest remediation sequence, including how you would confirm PID 813 belongs to the expected service before acting.
4. Why truncating unrelated visible log files would not solve this specific allocation.
5. The exact types of commands/evidence you would use to verify recovery after remediation.

Prioritize a graceful, minimal-impact fix.
Expected Result
  • Diagnosis: PID 813 still holds an open file descriptor to a deleted ~60 GiB file; blocks remain allocated until the descriptor closes.
  • Confirm ownership with ps/systemctl status app.service and related service metadata.
  • Preferred fix: gracefully restart/reload the owning service so the descriptor closes.
  • Random deletion/truncation of other visible files does not release the blocks held by this deleted inode.
  • Verify with lsof +L1, df -h /var, service health, and logs.
  • A reboot or force kill should not be the first recommendation.
